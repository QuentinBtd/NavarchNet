# AWS onboarding design and verification boundary

AWS is the first intended live provider. The development checkout implements opt-in role verification, read-only observations and metadata-only adoption; provisioning and AWS mutation remain disabled. The executable fake catalog still rejects AWS. No live AWS API call, paid resource, live connectivity test or cleanup has been performed: SDK replay, loopback protocol fixtures and real disposable PostgreSQL are the verification boundary. Do not enable live access for this mission without separate explicit role/account/budget authorization.

## Implemented read-only access and operator prerequisites

Enable only in production OIDC mode with `NAVARCHNET_AWS_READ_ONLY=true` and an explicit `NAVARCHNET_AWS_REGIONS` allowlist. The official AWS SDK loads the controller's standard credential chain lazily, then performs STS AssumeRole for the selected target role. NavarchNet accepts no permanent access-key fields. Target sessions request 900 seconds, cache only unexpired temporary credentials in memory, refresh near expiry, and request a unique actor-hash/UUID session name. GetCallerIdentity verifies account and exact role name before registration or scanning. Successful registration verifies identity, not every read permission: discovery may still fail closed with a permission error. SourceIdentity and session tags are not currently set. Ordinary tests never evaluate ambient credential profiles.

Target role trust must name the specific controller principal, not a wildcard AWS principal. The controller separately needs `sts:AssumeRole` on the exact target role ARN. For third-party/confused-deputy arrangements, require a per-onboarding ExternalId and match `sts:ExternalId` in the target trust policy; NavarchNet forwards the exact value. ExternalId is not an AWS credential, but is stored only in private role configuration and excluded from read-only views/audit payloads. If constraining `sts:RoleSessionName`, allow the generated `navarchnet-*` format. Policies requiring SourceIdentity, session tags or a per-request MFA token are not yet supported by this helper. Validate the complete trust arrangement independently before authorized live qualification.

The implemented target-session policy permits only the following exact actions in the registered region (`aws:RequestedRegion`), explicitly denies other actions and explicitly denies these actions in other regions. It is not a substitute for the role's own least-privilege policy. AWS IAM evaluation has not been live-tested here.

- EC2: `DescribeVpcs`, `DescribeSubnets`, `DescribeRouteTables`, `DescribeTransitGateways`, `DescribeTransitGatewayVpcAttachments`, `DescribeNatGateways`, `DescribeInternetGateways`, `DescribeAddresses`, `DescribeTransitGatewayRouteTables`, `GetTransitGatewayRouteTableAssociations`, `GetTransitGatewayRouteTablePropagations`.
- RAM: `GetResourceShares`, `GetResourceShareInvitations`, `ListResources`, `ListPrincipals`.
- STS: `GetCallerIdentity` for identity verification. AWS documents that this operation needs no identity permission; it is nevertheless explicitly listed in the session policy.

The current EC2/RAM service-authorization references list no resource-level ARN restriction for these read actions, so the inline policy uses Resource `*` with exact actions and region constraints, not `ec2:*`/`ram:*`. RAM resources and principals are filtered to `ec2:TransitGateway`; share/invitation enumeration can include other account RAM metadata and does not prove an invitation is for a TGW. Invitations are never accepted. Consult the current references in [sources](sources.md) and independently validate account-specific trust/role policies before deployment.

STS and RAM use official generated Rust SDK clients. EC2 uses a typed signed Query adapter (`aws-sigv4`) rather than the full generated EC2 crate; see ADR 0004. Individual XML responses, depth/nodes, aggregate EC2 bytes, retries, pages/tokens and resource counts are bounded. RAM uses SDK pagination/resource limits; it does not share the EC2 raw-body byte counter. A shared semaphore admits one verification/discovery at a time; HTTP timeouts include admission. A partial scan is never published as completed.

Supported observations include VPC/subnet CIDRs and AZ IDs, VPC routes (including IPv6/prefix-list destinations, unknown targets and blackhole state), main/explicit associations and their reported readiness state, TGW/attachment/route-table metadata, NAT availability mode/connectivity type, IGW/EIP metadata, provider-reported public/private IPs and RAM relationships. The topology API/UI conservatively selects an observed explicit or implicit-main table for each subnet, or reports a typed unresolved reason. Unknown/transitioning state, duplicate records and unverified/cross-VPC ownership never become a successful selection. Legacy missing state remains unknown without rewriting the snapshot. This is not full effective-route resolution. TGW route contents, security-group/NACL effects and complete egress/isolation analysis are not implemented. Snapshot completeness is only for supported queries. No observation grants ownership, executable routing or measured connectivity.

Scoped TGW association/propagation reads run for each discovered TGW table, with table ID in each signed request, independent bounded pagination and the same aggregate EC2 body budget. Their typed fields retain attachment/resource IDs, resource type, reported state and route-table announcement ID. A separate 10,000-relationship aggregate limit is enforced during capture and persistence. `null` means not queried (including legacy observations); an empty list means a completed empty read. Permission failures, missing collections, pagination cycles and duplicate links abort the scan and preserve the prior snapshot. Reported relationships are not proof of effective forwarding, return routes or isolation.

A future live mutation policy must be derived from the reviewed action set and ownership tags/resource ARNs: attachment create/accept, TGW association/propagation/routes, owned VPC routes, NAT/EIP/VPC/IGW/subnet resources and necessary RAM operations. The current session factory cannot be used for those actions. No deployment-ready mutation/trust policy or live permission qualification is claimed. Metadata consent is restricted to an owned VPC or TGW on the current completed snapshot; it does not adopt child routes or authorize any cloud write.

## Two accounts, two administrative boundaries

The network account owns the regional TGW, its route tables/associations/propagations and egress infrastructure. Application accounts create/manage their VPC attachments and selected owned VPC routes. A shared-TGW consumer cannot administer the owner's TGW route tables. Shared-subnet participants are not VPC owners; unsupported ownership/topology must be rejected.

AWS RAM sharing within an enabled AWS Organization has different invitation behavior from standalone-account sharing. Discover the actual share and invitation state. Explicitly surface pending invitations/attachment acceptance and require the appropriate account role for each action; do not blindly auto-accept unrelated invitations. Map zones by AZ ID across accounts, never AZ name.

## Route and ownership acceptance

A usable live plan must include individual managed resources, exact forward and return route destinations, resource readiness and owner-role prerequisites. Disable unintended TGW default association/propagation and verify existing manual propagations and more-specific routes. Reject overlap, unsupported attachments, conflicting unmanaged defaults, unsupported NAT mode, unsupported AZs and unknown ownership. Existing private-destination routes and CIDR specificity can invalidate an isolation claim even when a default route exists.

Adoption must identify exact resource IDs, owner account, routes permitted to change, existing traffic impact and excluded resources. A tag alone is not blanket authorization to replace every route. Do not destroy old connectivity before replacement prerequisites are ready. Never call an AWS sequence atomic; retain partial/ambiguous outcomes and observe before retries. Real AWS external-effect stale-worker safety needs dedicated implementation and tests beyond transactional fake effects.

Use zonal public managed NAT first, explicitly distinguished from current regional NAT availability mode (ADR 0002). IPv4 only. NAT64/IPv6 and cross-region fallback are unsupported. Show resource state, calculated paths and actual probes separately; no untested path is healthy.

## Cost and future NAT instances

Estimate current regional prices and expected traffic for managed NAT hours/data processing, TGW attachment hours/data processing, public IPv4 addresses, relevant AZ/inter-region/Internet transfers and any compute/probes. Do not claim a fixed saving from centralization; extra TGW processing can reverse a NAT-count saving.

Evaluate fck-nat later rather than building a new NAT engine. ENI/EIP identity, instance bandwidth/packet limits, OS maintenance, availability replacement, stateful connection reset and cross-AZ/inter-region costs must be measured. Preserving an EIP does not preserve connection state. No NAT instance or tunnel/BGP overlay is deployed in V1 bootstrap.
